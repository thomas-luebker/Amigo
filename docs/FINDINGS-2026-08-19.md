# Findings — 2026-08-19/22

A working session that shipped 0.7.2, built most of 0.7.5, found four
upstream bugs, diagnosed a hang, and — more usefully than any of that —
established why three earlier attempts at the same investigations had
produced nothing.

Kept separate from `BACKLOG.md`: that file is the working list, this is
the evidence and the reasoning behind it.

---

## 1. Upstream bugs in the vendored unix port

All four are in `vendor/WinUAE`, none originate in this project. Fixes
live in `patches/0001-ios-port-fixes.patch`, which is the record. We do
not proactively file port-side findings upstream — see the note at the
end of this section.

### 1.1 `clipboard_vsync` gated on `initialized` — deadlock

`od-unix/clipboard.cpp` opened with:

```c
if (!filesys_heartbeat() || !clipboard_data || !initialized) return;
```

`od-win32` has never had `!initialized` there, and it must not: the
Amiga-side clipboard process (`filesys.asm`, `clipboard_proc`) blocks on
`Wait(SIGBREAK_CTRL_D)` at `cfloop2` **before** it can open
`clipboard.device` and call back with mode 15 — and mode 15 is the only
thing that sets `initialized`. That signal is sent from
`clipboard_vsync_cb` → `uae_Signal(task, 1 << 13)`.

So the host waited for an init that could only happen after a signal the
host refused to send. Circular and permanent.

**Symptom:** `clipboard task init` appears in the log, `clipboard
initialized` never does, and Amiga → host clipboard is dead forever.
iOS → Amiga was unaffected because the keystroke path bypasses the
handshake entirely, which is why the feature looked half-working.

**Fix:** remove the condition. That one line was the entire fix.

### 1.2 `write_host_clipboard_text` / `_image` have no iOS path

Both tried `SDL_SetClipboardData`, then fell back to `/usr/bin/pbcopy`
via `popen` — which cannot exist on iOS. SDL3's UIKit backend does not
deliver either, so **both directions failed silently**: no error, no log,
nothing on the pasteboard.

**Fix:** write `UIPasteboard` directly from `UAEBridge.mm`. Text and
images both. Prefer PNG, then TIFF, then BMP — `UIImage` decodes all
three through ImageIO, so it does not matter which encoders a given build
configured (libpng is conditional on `PNG_FOUND`; ImageIO is not).

### 1.3 `clipboard_put_text` has no dedupe

Latent on desktop because nothing there polls. It became critical the
moment we (wrongly, see §4.1) introduced polling: `got_data` then arrives
every second and **every poll rewrote the host clipboard**. On iOS that
means anything the user copies in another app is destroyed within a
second, permanently.

It would have passed every test we were running. A nonce-and-log test
checks that data arrives — it cannot notice that data arrives *too often*.

**Fix:** compare against `last_host_clipboard` before writing.

### 1.4 RGA refresh slot with NULL pointer

`custom.cpp` bitplane (~9365) and sprite (~9691) writers pass `NULL`
deliberately, relying on `bitplane_rga_ptmod()` to install the pointer
later. But that call sits under `if (!custom_disabled)` in `do_cck()`
while `handle_rga_out()` below it does not, and `custom_disabled` follows
`ad->picasso_on`. A slot already in the pipe when RTG switches on
therefore never gets its pointer, and the refresh branch dereferences
NULL.

**Resolution: unresolved, and the proposed fix was withdrawn.** Toni
proposed dummy pointers rather than a test in the hot path, we applied
them, and he then **reversed it the next day**: they are detected as a
conflict and corrupt bitplane DMA pointers in cycle-accurate mode.
Reverted to `NULL` at both sites.

That reversal mattered here more than it did upstream. The dummy pointers
were in a build about to go to TestFlight, and our test machine is a
68040 with `cycle_exact=false` — the one configuration that would never
have shown the fault. An A500 quickstart, which is what most people run,
has cycle-exact on.

> **"Tested on device" means tested on ONE configuration.** Cycle-exact
> was off on the machine we happened to use, so a whole class of
> corruption was invisible to us.

**We could never reproduce the original crash.** Our NULL check logs
`reg` and `type` on first occurrence and has *never fired* — across two
days, with dummies, without them, and with the check removed entirely so
a NULL would segfault outright. The crash predates the check. So there
are no `reg`/`type` bits to give upstream, and Toni reasonably declines
to add a NULL check without understanding the mechanism —
`sync_equalline_handler()` clears the RGA queue, and `CYCLE_REFRESH` may
not be the only type that can cause it.

Our own guard stays locally: it is the difference between a crash and a
skipped refresh.

A separate false lead worth recording: BEAMCON0 reading `0020` at the
hang looked significant, but bit 5 is the PAL/NTSC bit and this is a PAL
config — so it was P96 setting PAL on a machine already PAL, not a
mid-boot mode switch.

> **Upstream policy.** We do not proactively file port-side findings.
> That is *not* because Toni is uninvolved — he replied personally within
> a day on both patches. The distinction: don't send him every small
> finding; do finish the exchange under way.
>
> **Finished 2026-08-21.** He was told the bits do not exist and why,
> and thanked for the dummy-pointer reversal. The two earlier offers
> (`clear_rga()`/`check_rga_out()` variants, mousehack as an opt-in prefs
> flag) were **not renewed** — spare-time project, no capacity for a
> back-and-forth, and an offer that cannot be upheld is worse than none.
> The hypothesis above was cut from the sent reply; it lives here.

## 2. The boot hang — diagnosed

**Reproduction:** boot normally → several Intuition screen switches
(left-Amiga+M) → reset → hang on the boot that follows. App stays alive,
emulation stops, display freezes.

Six plain cold launches were clean, so it is **not** a boot-order bug.
The screen-switching state is required.

**Captured state** (watchdog, §3.2), sampled twice a second apart:

```
hangdiag[stall]:    pc=00f04004 stopped=0 intena=602c intreq=1040
                    bplcon0=0200 ERSY=0 genlock=0 beamcon0=0020 vpos=19 hpos=1
hangdiag[stall+1s]: (byte-identical)
```

Against the four candidates Toni offered:

| Hypothesis | Verdict | Evidence |
|---|---|---|
| STOP waiting on an impossible interrupt | ruled out | `stopped=0`; `intena` matches a healthy machine |
| BPLCON0 ERSY set without genlock | ruled out | `ERSY=0`, `genlock=0` |
| CPU polling something that never ends | ruled out | `pc`, `vpos`, `hpos` identical across a full second |
| BEAMCON0 written at an unsafe position | present, not implicated | `0020` at hang vs `0000` healthy |

The decisive fact is the third row: **nothing is executing at all.** A
guest-side poll would still advance the beam. `vpos` frozen means the
host emulation thread is not running.

**Conclusion — and it was right.** The PC sits in the **rtarea** (a trap
into host code) with the host thread stopped, always immediately after
`hardfile thread starting, unit 0`.

**Root cause, found 2026-08-20.** `hardfile.cpp` `start_thread()`:

```c
uae_start_thread(_T("hardfile"), hardfile_thread, hfpd, NULL);
while (hfpd->thread_running == 0)
    sleep_millis(1);
```

`uae_start_thread` returns 0 when `pthread_create` fails, and that return
was **ignored**. The loop then waits forever, on the emulation thread,
for a thread that was never created. `hardfile_thread` sets
`thread_running` within microseconds of entry
(`uae_set_thread_priority` is a no-op on this port), so any wait of real
length means it is never coming.

Every captured symptom follows from that one unchecked return.

**Fix:** check the return and give up with a log line; bound the
remaining wait at 3s; and have `uae_start_thread` log `pthread_create`'s
errno. A freeze becomes a hard drive that fails to open, plus a
diagnosis.

**Still open:** *why* `pthread_create` fails. Thread exhaustion across
repeated resets is the obvious suspect, since several resets are needed
to provoke it. The next occurrence will name it in the log.

> **The baseline earned its keep.** A *healthy* idle boot reads
> `stopped=1` — the Kickstart idle loop. Without having measured that
> first, the captured `stopped=0` would have read as confirmation of the
> STOP hypothesis rather than its refutation.

**Severity before the fix:** low but real. Reproducible with a deliberate
sequence; also hit once after ordinary use. Present in 0.7.2, which is
live, with no user reports.

> **A lesson about ignored return values.** This was not a subtle
> concurrency bug. It was a function that documents failure by returning
> 0, a caller that did not look, and a spin-wait with no bound. Two days
> of chipset hypotheses — refresh slots, ERSY, BEAMCON0, beam positions —
> for an unchecked `if`.

## 3. Diagnostic infrastructure built

The most reusable output of the session. Three earlier attempts at these
investigations produced nothing, and it was the instruments failing, not
the tests.

### 3.1 File-backed log — `Documents/amigo-log.txt`

`write_log()` already mirrors to `debugfile` when set. It is now opened
in `main()` (`UAEMain.mm`), **before anything Amiga-side runs**, with
`always_flush_log`.

- Survives console drops, hangs, kills and reinstalls
- Rotates to `amigo-log.prev.txt` on launch, so the session *before* a
  crash survives the restart that follows it
- Visible in the Files app — a tester can send one with no tooling

Pull it with:

```
xcrun devicectl device copy from --device <id> \
  --domain-type appDataContainer --domain-identifier de.amiga-imager.uae \
  --source Documents/amigo-log.txt --destination ./amigo-log.txt
```

**Two traps found the hard way.** Opening at overlay-install is too late —
the crash we were chasing happens before SDL's window exists, so the log
was never opened at all. And opening `"w"` truncates, destroying exactly
the log you want after a crash.

**Known gap:** Swift `NSLog` does *not* reach this file; only the core's
`write_log` does.

### 3.2 Hang watchdog

A `pthread` that watches `vpos` and, when the beam stops moving, dumps
CPU/interrupt/chipset state twice a second apart. Two samples is what
distinguishes **blocked** from **spinning** — the one thing the earlier
logs could never settle.

It **must** be on its own thread: when the emulation wedges, the SDL main
thread wedges with it, so nothing scheduled there can ever report.

It also logs one line on every boot as a self-check. A watchdog that
silently fails turns "we captured nothing" into what looks like "nothing
happened".

### 3.3 Automated stress — `test/autostress` (DO NOT MERGE)

Injects left-Amiga+M screen switches and a reset on a timer, reproducing
the hang sequence with no human in the loop. Caught the hang in ~5
minutes where manual attempts had been hit-and-miss.

### 3.4 Making a test fail loudly

To answer whether Toni's dummy pointers held, the NULL guard was removed
on a branch. With the guard in place a clean run only shows *no NULL slot
occurred*; it cannot show the fix *prevented* one, because the guard
would have absorbed it either way.

Three builds, same sequence:

| build | result |
|---|---|
| dummies + guard | hang |
| dummies, **guard removed** | same hang, **no crash** |
| `NULL` restored + guard (control) | same hang |

Row two is the evidence his fix holds. Row three rules out the confound
that his change caused the hang.

### 3.5 Layout diagnostics — `make_video_layout()` (2026-08-21)

Three `write_log` lines, all file-log only, all shipping in build
`20260824`. Added because screen-geometry complaints are impossible to
diagnose from a screenshot and had already burned a session (§4.5).

| line | fires | answers |
|---|---|---|
| `iPadUAE statusbar: scale=…` | on LED-bar scale change | the original LED sharpness work |
| `iPadUAE layout: out=… safe=… inset=… status=… frame_area=… src=… fit=…` | only when the geometry changes | which term is eating picture height |
| `iPadUAE aspect_fit: setter called with N` | at scene connect + each menu toggle | whether the Swift setting reached the core |

The middle line is the important one. Read it as: `out` is the drawable,
`safe` is what survives the safe-area inset, `inset` is the keyboard
reservation, `frame_area` = `safe_h - status_height` is what the picture
actually gets, and `src` is the emulated source. **In Stretch (`fit=0`)
the picture fills `frame_area` by construction — so any black band at all
means `frame_area` is smaller than you expect, and the line says which of
`safe`, `inset` or `status` did it.**

A worked example, iPhone 17 portrait:

    out=1206x2622  safe=0,186 1206x2334  inset=0.000
    status=1  frame_area=2333  src=756x576  fit=1

186 px of safe-area at the top; no keyboard reservation; so 2333 px for a
756x576 source, which at uniform scale is limited by width to x1.595 and
draws 1206x919 — 39% of the height, the rest black. Not a bug.

> Note: regenerating `patches/0001-ios-port-fixes.patch` from the full
> vendor diff on 2026-08-21 swept the statusbar line **into** the patch,
> resolving a long-standing one-hunk drift between the submodule and the
> patch by inclusion rather than removal. `apply-patches.sh` verifies
> clean and idempotent.

## 4. Mistakes made, and the patterns behind them

Recorded because the patterns recur, not for their own sake.

### 4.1 A dead instrument reads exactly like a quiet system

`devicectl --console` went silent three times while the process stayed
alive and the app kept running. The log simply stopped growing.

Cost: the clipboard change hook was declared dead and a **polling
workaround was shipped on the strength of it** — a whole mechanism, plus
a dedupe guard to stop that mechanism destroying the user's clipboard,
solving a problem that did not exist. Two further test rounds were void.

The same class of error appeared twice more: a `strings` scan that could
not see the section it was asked about (caught only because a control
string was checked), and logs read *before* the event had landed.

**Rule:** verify the instrument is live before believing a negative
result. Use a control.

### 4.2 Read paths that write

Two regressions, same root cause — code whose job was to *read* state
wrote an inferred value back:

- **DF1 silently disabled.** The shipped `default.uae` has no
  `floppyNtype` lines, and in WinUAE absent means *default* — DF0 **and**
  DF1 — not disabled. The code parsed the text, read absent as `-1`,
  concluded "one drive", and a `didSet` wrote `floppy1type=-1` back.
  Merely reading the machine mutated it.
- **RTG stopped activating.** A cosmetic CRT toggle drove
  `gfx_filter_bilinear` across *all three* `gf[]` slots including
  `GF_RTG`, on every launch.

A third instance nearly shipped: `statusline_set_multiplier()` ignores
its arguments and reads a **persisted** pref, so a device-derived value
would have reached a config file.

**Rule:** a mirroring property must not have a `didSet` that writes. Only
an explicit user action changes the machine.

### 4.3 Verifying the mechanism instead of the outcome

Warp was wired to the core's own `warpmode()`, confirmed to compile, and
called done. It was never timed. `warpmode()` sets `gfx_framerate = 10` —
the display draws **one frame in ten**, so the machine *looks* frozen and
*feels* slow while emulation runs uncapped underneath.

That single setting probably also explains the separate "display stays
stale after a WHDLoad title exits" report from the same afternoon, which
has not recurred since warp was removed.

**Rule:** verify the outcome, not that the right function was called.

### 4.4 Config changes silently reverted

`markBootStable()` cleared the risky-change marker once per app
**launch**, 30s after the overlay installed. A machine change restarts the
emulator, not the app — so any change made later in a session stayed
armed, and a force-quit made the next launch restore `.last-good.uae`.

**Every machine setting was affected.** An EAB user reported it
independently as "it's not saving to .last-good unless I overwrite the
config myself" — a precise description of a bug that was fixed the same
week. `snapshotBeforeRiskyChange` now arms its own 30s timer.

### 4.5 Four hypotheses, zero measurements (2026-08-21)

A report of "too much black" on iPhone produced, in order: a stale
keyboard inset, a coordinate-space mix in `frac`, an over-aggressive
crop, and a "the Picture setting never reaches the core" bug. **All four
were wrong**, and the fourth was one step from being reported to the user
as a shipping defect.

What settled it was a single `write_log` printing every term that feeds
the layout, and a second at the Swift→core boundary. Once those existed
the answer took one run: `inset=0.000`, `fit=1`, and a source that simply
cannot fill a 19.5:9 window. Before they existed, four rounds of reading
the code produced four confident and different answers.

Work was also done on the strength of those wrong answers — a whole
"Fill" picture mode was designed, built, shipped to a device, and
reverted, because the geometry hypothesis was never checked first.

**Rule:** when a report is about *observable state*, the first action is
to print the state. Not to read the code that computes it. A log line is
cheaper than one wrong hypothesis, let alone four.

### 4.6 A probe that silently does nothing looks like evidence

To test whether the Picture setting reached the core, the pref was pushed
onto the device with `devicectl ... copy to Library/Preferences/…plist`
and the app relaunched with `--terminate-existing`. Both runs reported
`fit=1` regardless of the value pushed, which read as a clean, repeated
demonstration of a real bug.

**The push never took effect.** iOS preferences are owned by `cfprefsd`
and cached in-process; `--terminate-existing` makes the app flush its own
cached values *over* the pushed file on the way out. Both readings were
the probe failing, not the app.

This is 4.1 ("a dead instrument reads exactly like a quiet system") in a
new costume, and it was not recognised in time. **Rule:** a probe must
prove it changed something before its output counts as evidence — read
the value back through the same path the app uses, not from the file you
just wrote.

## 4b. The LHA stack overflow — the 0.7.1 field crash (2026-08-21)

Five App Store crash reports on 0.7.1, all one signature, all one user
(iPad16,4, iOS 27.0 beta), four within two minutes as they retried.

    __stack_chk_fail
    lha_make_table(short, unsigned char*, short, unsigned short*)
      decode_c_st1 -> decode -> archive_access_lha -> archive_getzfile
      -> zfile_fopen -> drive_insert -> DISK_examine_image -> DISK_hsync

They inserted a **`.lha` as a floppy** — how essentially every WHDLoad
title is distributed, so a mainstream path, not an exotic one.

### Why the existing guard did nothing

`lha.h` contains:

    #define error write_log

So upstream's own validity check —
`error(_T("make_table()"), _T("Bad table (5)\n"))` — **logged the problem
and fell straight through into the overflow**. The guard has been
decorative for as long as that `#define` has existed. This is the same
shape as 4.1 and 4.6: an instrument that looks like protection and isn't.

### Three separate overflows, all reachable from archive bytes

1. **`lha_make_table`** — `count[bitlen[i]]++` where `count[17]` is a
   stack array and `bitlen[]` is `unsigned char` from the archive.
   `read_pt_len` can legitimately produce bit lengths up to **19** (the
   `c == 7` mask loop walks 12 further bits), so this is reached in
   normal corrupt-data handling, not only in contrived cases.
2. **`read_c_len`** — `n = getbits(CBIT)` with CBIT=9 gives up to **511**
   while `c_len[NC]` holds **510**: a one-past-the-end write.
3. **`read_c_len` run lengths** — `c = getbits(CBIT) + 20` reaches
   **531**, and `while (--c >= 0) c_len[i++] = 0;` had no bound. Not a
   canary nudge: a bulk overwrite of adjacent globals.

The fix bounds all three, plus the Huffman tree walk (`h_left`/`h_right`
are `2 * NC - 1` = 1019 entries) and a cycle guard. On rejection the
table is zeroed, so a broken archive decodes to garbage — the right
outcome — instead of killing the process.

### Verified, not assumed

A host harness drives the **real** decoder (`lhamaketbl/huf/slide/crcio/
shuf/dhuf/larc`) over real Aminet archives; only four symbols needed
stubbing (`write_log`, `zfile_getc/_fread/_fwrite`).

| | valid.lha | 150 fuzzed variants |
|---|---|---|
| upstream | 118 members, exit 0 | **139 crashes** (SIGSEGV 75, SIGBUS 61, SIGABRT 3) |
| fixed | 118 members, exit 0, guard never fires | **0 crashes** |

Decoded-output checksum on the valid archive is **identical** between
upstream and fixed (`fnv=8392c356fac831b1`, 118 members), so good
archives are bit-for-bit unaffected.

> [!important] Decision 2026-08-21: fixed in our patch, not sent upstream
> This is upstream WinUAE code and security-relevant, but it stays ours.
> The reproduction (real archive + harness + before/after exit codes) is
> in the scratch notes if that is ever revisited.

> [!warning] Two harness bugs that produced confident wrong answers
> **LHA level-1 headers put extended headers between the base header and
> the compressed data, and the "skip size" field covers them.** Feeding
> those bytes to the decoder made a perfectly valid archive report 459
> broken Huffman tables — which read exactly like "the fix breaks valid
> archives". The first corrupt test file was damaged in the same region,
> so it never corrupted a compressed stream at all. Correct walk:
> `base_end = off + 2 + hsize`; the last two bytes of the base header
> give the first ext-header size, each ext header's last two bytes give
> the next; `data = base_end + ext_total`, `len = skip - ext_total`.

## 5. Platform and tooling gotchas

- **Build numbers are date-based** (`20260819`). `build-release.sh`
  defaulted to `git rev-list --count HEAD` — currently 159, far below the
  last uploaded build — so an unattended release would have been rejected
  on upload. Fixed to `date +%Y%m%d`.
- **…and `date +%Y%m%d` has now been outrun too (2026-08-21).** ASC held
  `20260823` on 2026-08-20, so today's default `20260820` was *lower*
  than the last upload and would have been rejected. Pass the number
  explicitly until the calendar catches up.
- **Release upload cannot be driven from the CLI on this Mac.** No iOS
  Distribution certificate exists in the keychain — only *Developer ID
  Application*, which is for Mac distribution outside the App Store. So
  `xcodebuild -exportArchive` fails with `No signing certificate "iOS
  Distribution" found`. Organizer succeeds because it cloud-signs through
  Xcode's Apple ID session, which `xcodebuild` cannot see (`error: No
  Accounts`). The ASC API key fails a third way — `Cloud signing
  permission error` — because it is App Manager, and cloud signing needs
  **Admin**.
- **`devicectl` reports a locked device as a connection failure.** A
  locked iPhone answers `device info details` but refuses to mount the
  developer disk image, and the surfaced error is `Connection reset by
  peer` / `CoreDeviceError 4000`, which reads as a networking or pairing
  problem. The real message is buried:
  `kAMDMobileImageMounterDeviceLocked`. Unlock before diagnosing further.
- **Pushing a `UserDefaults` plist to a device does not stick.** See
  §4.6 — `cfprefsd` and the app's in-memory cache overwrite it.
- **Organizer only indexes `~/Library/Developer/Xcode/Archives/`.**
  `build-release.sh` writes to `build/`, so its archives are invisible
  there. Copy into a dated folder to make one appear.
- **Xcode needs a signed-in account** for anything requiring a *new*
  provisioning profile. Existing profiles work without one, which is why
  device builds succeeded while Mac builds and App Store export failed
  with `No Accounts`. iCloud was new in 0.7.2, so the distribution
  profile had to be regenerated.
- **The data container UUID changes across reinstalls**, so absolute
  media paths in `default.uae` go stale. `healPaths` rewrites them.
- **`devicectl` refuses to launch on a locked device** (`reason: Locked`).
- **Never combine a retry loop with `--terminate-existing`.** `--console`
  exits non-zero when the *stream* drops on a healthy app, so the loop
  kills something that is working. Two such loops running unnoticed looked
  exactly like the app crash-looping.
- **The M4 iPad is also an amimcp fleet node.** Every install kills the
  guest and any `amiagent` session on it. Coordinate first.

## 6. Working with the guest side

`amiagent` was decisive three times, and the principle generalises: **the
guest can prove what the host can only infer.**

- `TASKLIST` showed `UAE clipboard sharing` alive at pri -10, which
  distinguished "parked waiting for a signal" from "died at the `DEVS:`
  Lock" — unobtainable from the host.
- It caught that `filesys.asm` never tests the `CBD_CHANGEHOOK` `DoIO`
  result, demolishing an inference a conclusion had been built on.
- It caught that installs wipe `RAM:` and the clipboard, which had made
  one test round void by construction.

When host and guest disagree, measure on the side that can observe.
Reach for it early rather than after three theories.

## 7. Performance, measured against real hardware (2026-08-22)

The first time Amigo's speed has been *measured* rather than described.
Method: one benchmark, cross-compiled with bebbo's amiga-gcc at
`-m68000`, so the **identical binary** runs on the emulated 68040 and on
the real A4000's 68060. It times itself with `DateStamp` (50 Hz), so
host-side latency cannot contaminate the numbers. Both machines were
driven over `amiagent`.

The workload, in full — nothing here needs a CPU newer than a 68000:

    static volatile unsigned long sink;          /* defeat the optimiser */

    static long bench_int(void) {                /* integer + shift      */
        long t0 = now_ticks();
        unsigned long a = 1, i;
        for (i = 0; i < ROUNDS; i++) { a = a * 1103515245UL + 12345UL; a ^= a >> 7; }
        sink = a;
        return now_ticks() - t0;
    }

    static long bench_mem(APTR buf, ULONG size, int reps) {   /* memcpy  */
        long t0 = now_ticks();
        for (int r = 0; r < reps; r++) {
            memcpy((char *)buf + size / 2, buf, size / 2);
            sink += ((unsigned char *)buf)[r & 63];
        }
        return now_ticks() - t0;
    }

`now_ticks()` is `DateStamp()` folded to `ds_Minute * 3000 + ds_Tick`.
The buffers are 256 KB from `AllocMem` with `MEMF_FAST` and `MEMF_CHIP`
respectively — the same code over the two memory types is the whole
point.

### The numbers

iPad Pro 13" (M4), Amigo, `cpu_speed=max`, `cachesize=0` (no JIT),
`cycle_exact=false`, versus an A4000/060:

| Workload | emulated 68040 | real 68060 | Amigo |
|---|---|---|---|
| integer, 3M rounds | 602 ms | 2,940 ms | **4.9x faster** |
| memcpy, Fast RAM | 112 ms | 1,480 ms | **13.2x faster** |
| memcpy, **Chip RAM** | 112 ms | 11,540 ms | **103x faster** |
| DOS `copy RAM: -> NIL:` | 33.7 MB/s | 13.7 MB/s | 2.5x faster |
| hardfile write / read | 35.3 / 34.0 MB/s | — | — |
| amiagent round-trip | 3 ms | 15 ms | 5x faster |

The integer figure reproduced at 602 ms in a 10x-scaled re-run (30M
rounds, 6,020 ms), so it is not a quantisation artefact of the 20 ms
tick.

### Chip RAM is free here, and that is the interesting result

On real hardware Chip RAM is **7.8x slower than Fast RAM** — chipset
contention, exactly as it always was. Under Amigo the two are
*identical* (112 ms against 112 ms), because both are ordinary host
memory.

Two consequences, neither of them a bug:

- Chip-bound software — which is most games and demos — runs
  **disproportionately better** than the 4.9x CPU figure suggests.
- Anything whose timing was tuned around Chip RAM being slow behaves
  differently. This is inherent to `cycle_exact=false`; the 68000 preset
  turns cycle-exactness back on, which is precisely why it exists.

### Storage is not a bottleneck anywhere

The hardfile runs at the same ~34 MB/s as the RAM disk, and DOS file
copy beats the real 060 by 2.5x. Guest clock rate tracks host wall clock
to within the resolution of `date` (+/-1 s over a 20 s window). No
evidence of drift.

### Two measurement traps, both of which produced a false finding first

**`ipad-4.local` costs 3.3 s per connection.** It resolves to
**169.254.155.140** — a *link-local* address — and the amimcp client
opens a fresh socket per request, so every request paid an mDNS lookup.
That produced two confident and completely wrong intermediate results: a
"1.15 MB/s guest I/O ceiling" (it was a fixed ~3.4 s cost that did not
scale with data size — 2 MB and 4 MB took the same wall time, which is
what gave it away) and a "3.25 s TCP connect in the bsdsocket
emulation". **By IP, connect takes 0.002 s — faster than the real
A4000** — and throughput is 34 MB/s. The socket emulation is fine.

The tell was the control: the same test against the A4000 by IP was
instant. *Always measure the reference machine the same way.*

That link-local address also means the iPad **has no DHCP lease on the
LAN** — it was reachable over the USB/devicectl tunnel, not Wi-Fi. Worth
establishing before trusting any network measurement.

**A DOS requester deadlocks the agent.** `list amibench:` for a volume
that does not exist opens a "Please insert volume" requester; amiagent
runs one command at a time, so everything blocked behind it. `BREAK`
does not clear it — Ctrl-C cannot dismiss a system requester. It needed
a click on Cancel (`input_click`; `ui_click("Cancel")` did not match the
gadget). Never name a volume that might not exist.

### What this says about `cpu_idle`

Both the iPad config and the Mac "Designed for iPad" container run
`cpu_speed=max` with **no `cpu_idle` line**, so the STOP-state host sleep
never engages on either. The mechanism, for the record — `custom.cpp`
`vsync_handler_render()`:

    int mv = 12 - currprefs.cpu_idle / 15;
    if (mv >= 1 && mv <= 11) { ...arm sleepmode... } else { reset_cpu_idle(); }

At `cpu_idle = 0`, `mv` is 12, which falls outside the band, so
`reset_cpu_idle()` runs on **every frame** and the host never sleeps.
That also explains the oscillation recorded in `BACKLOG.md` -> *Power /
energy*: the band is narrow and inverted — `cpu_idle=15` gives a 0%
stopped-lines threshold (sleeps almost always) while `cpu_idle=150`
gives 90% (sleeps almost never). This is evidence for that existing
item, not a new one; the key was added deliberately in `8414a8e` and
left at 0 pending exactly this tuning.
